# Trace schema (v1)

The contract between every harness component: the runner and capture layer
*write* traces; the viewer, inspection CLI, and evaluators *read* them. Keep
this doc and `ebrowse_evals/trace/records.py` in sync — the dataclasses are
the normative field list; this doc records the intent and the rules.

## Run directory layout

```
runs/<name>/
  events.jsonl   # append-only stream of typed records, one JSON object/line
  blobs/         # content-addressed payloads: blobs/<hex[:2]>/<sha256><suffix>
```

Blob refs are `"sha256:<hex>"`. Content addressing dedupes identical payloads
(unchanged pages across steps share one screenshot/DomSnapshot blob).

## Rules (binding)

1. **Grow by addition only.** New record types and new fields are fine;
   renaming/repurposing existing ones is not. Readers must skip unknown record
   types and preserve unknown fields (`Record.extra` round-trips them).
   `run_meta.schema_version` bumps only on a break we failed to avoid.
2. **Large payloads go through the blob store**, never inline —
   `events.jsonl` stays skimmable/greppable.
3. **Everything is keyed by entities**: `step` (1-based agent tool-call
   index), plus `request_id` / `ref` / `sid` in fields where applicable.
   Investigations are entity-centric ("trace @e12"), not log-centric.
4. **Two logging tiers.** Tier 1 (always on, small): step facts, timings,
   ref lifecycle, diff verdicts, action execution, `anomaly` records.
   Tier 2 is *not logged*: full pipeline decision traces are regenerated on
   demand by replaying the stored DomSnapshot through pure `core/` code.
5. `ts` = wall clock (unix), `mono` = monotonic (for durations). Fixture
   generators pass fixed values for byte-stable output.

## Record types

| type | one per | carries |
|---|---|---|
| `run_meta` | run (first record) | ids, prompt, fully **resolved** config, agent/model, git sha, ebrowse version + worktree/installed mode |
| `step` | agent tool-call | exact command, verbatim output, tokens/latency, per-phase `timing`, post-action `browser` state, `screenshot`/`dom_snapshot` blob refs (captured **unconditionally**), `request_id`, structured `error` |
| `browser_event` | page event | console / network_failure / dialog / navigation since previous step — unrecoverable if not captured live |
| `ebrowse_log` | internal event | `module` + `event` + structured `fields` (not prose), `level`, `request_id` joining it to a step |
| `anomaly` | pipeline surprise | the triage layer — a run's list should fit on one screen (ref_rebound, snapshot_truncated, element_moved, wait_timeout, section_reshaped, …) |
| `summary` | step range | post-hoc cheap-model summary for LLM navigation |
| `run_end` | run (last record) | outcome, totals (tokens, peak context, anomaly count), eval result |

A crashed run is still a readable trace: the reader tolerates a torn final
line and `validate` reports missing `run_meta`/blobs instead of failing.

## Tooling

- `ebrowse-eval validate <run-dir>` — structural check + one-line summary.
- Committed sample: `evals/tests/fixtures/sample-trace/`, generated by
  `python evals/tests/fixtures/generate_trace.py` (edit the generator, not
  the output). Build viewers/inspection tools against it.
